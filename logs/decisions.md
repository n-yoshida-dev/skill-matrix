## 2026-09-23 データはリポジトリ直下の `data/` に置き、判定は「学習ログ1件 = 1ファイル」で追記する

**論点**: 自分専用版の JSON（ロードマップ・判定・理解度）をリポジトリのどこに、どんな粒度で置くか
**結論**: リポジトリ直下に `data/` を新設する。`data/roadmap.json`（マスタ）、`data/judgments/YYYY-MM-DD-<短い名前>.json`（判定。学習ログ1件につき1ファイル。作ったら以後触らない）、`data/state.json`（理解度。CLI が毎回まるごと書き直す）。画面からは Vite のパス別名を通して読む
**理由**: データの持ち主は CLI（Go）と AI であって画面ではない。`backend/` `frontend/` と並ぶ第三のディレクトリにすると役割が読める。粒度を「1ログ1ファイル」にすると AI がやるのは新規ファイルを1個作るだけになり、**既存の判定を壊しようがない**。git の差分も「新規1ファイル」で読める。理解度は導出値（KNOWLEDGE.md 2026-08-09）なので1ファイルにまとめ、手で編集しないファイルとして扱う
**却下した代替案**: `frontend/public/data/` に置く（Vite の設定が要らず画面がすぐ読めるが、Go の CLI が `frontend/` の中を書き換える構図になり担当がねじれる）／全判定を `data/judgments.json` 1ファイルにためる（ファイル数は増えないが、AI が全文を書き直したときに過去分を壊す事故がありうる）／詳細項目1つ = 1ファイル（1回のログが複数項目に触れるので判定が複数ファイルに散り、履歴を追いにくい）
**確信度**: 高
**見直す条件**: 判定ファイルが数百件に達して一覧が扱いづらくなったら、年ごとのサブディレクトリ（`data/judgments/2026/`）に分ける

## 2026-09-23 学習ログ本文はリポジトリに置かず、`evidenceRef` で出どころを指す

**論点**: 学習ログ本文と `rationale`（判定の根拠。ログの引用を含みうる）をリポジトリに置くか。置くと CLAUDE.md「自分の学習ログの実データをコミットしない」と衝突し、公開の道が閉じる
**結論**: **ログ本文は置かない。** 判定1件に `evidenceRef`（根拠の出どころを指す文字列）を持たせ、そこから原文をたどる。`rationale` は置くが、指示書で「技術的な事実だけを書く。所属先・企業名・人名・転職活動・人事評価に関する記述を含めない」と縛る。**この縛りは `evidenceRef` にも同じくかける**（`evidenceRef` も同じ判定ファイルにコミットされるため）。これにより判定 JSON は実物をコミットでき、リポジトリを公開できる。`evidenceRef` の書式は `<種別>:<識別子>` の自由な文字列（例：`study:<リポジトリ内のパス>` / `cert:<資格名>/<年月>-合格` / `repo:<リポジトリ>@<コミット>` / `work:<期間>/<担当>`）。`domain.Judgment` に `EvidenceRef` を足す
**理由**: 「根拠の出どころ」と「判定」は別物で、正本の場所が違う。**学習ログの正本は `~/workspace/study`（Private リポジトリ）にあり、しかも出どころはログだけではない**（資格・業務・他アプリのコミットも根拠になる）。skill-matrix が正本を持つべきなのは判定（いつ・どの項目が・どのレベルに・なぜ）だけで、ログ本文を写せば study との二重管理になる。出どころを文字列で指す形にすれば、正本を1つに決める必要がなくなり、study が正本でない根拠もそのまま乗る。判定そのもの（「go-05 がレベル3になった。根拠は実装」）は技術的な情報で、公開して困らないどころかポートフォリオとして価値がある
**却下した代替案**: ダミーの判定だけ公開し実データは `.gitignore`（ルールとは一致するが、判定の履歴が git に残らず `skill-map.md` の代わりにならない）／ログも `rationale` も置いてリポジトリを Private のまま（study と二重管理になり、公開の道＝面接で URL を送る用途が閉じる。GitHub Pages も無料プランでは Public リポジトリのみ）／`rationale` すら置かない（項目詳細画面の「いつ・何を根拠に上がったか」が空になる）
**確信度**: 中（`rationale` と `evidenceRef` に固有名詞が混ざらないことを機械で保証できない。judgments は1ログ数行なので `git diff` の目視で拾える前提に立っている）
**見直す条件**: `git diff` の目視で固有名詞を拾い損ねる事故が起きたら、`verify` CLI に禁止語リストによる検査を足す。それでも不安なら公開をやめて Private に戻す（仕組みは変えずに済む）

## 2026-09-23 判定のとき、study リポジトリの学習ログを AI に自動で読ませる

**論点**: 判定のたびに学習ログを自分で AI に手渡すか、AI が `~/workspace/study` を自分で読みに行くか
**結論**: 自動で読ませる。根拠の出どころのパスは `sources.local.json`（`.gitignore` に入れる）に書き、指示書からそれを読ませる。判定済みかどうかは `data/judgments/` の `evidenceRef` の一覧と突き合わせて判断する
**理由**: 手渡しは毎回の手間になり、続かなければ画面のデータが増えない。判定済みの管理も `evidenceRef` があれば自動で付く（既に出てきたログは飛ばす）。パスを設定ファイルに切り出すのは、公開リポジトリに自分のローカルのディレクトリ構成を書かないため（`../CLAUDE.md`「ハードコードは禁止」と個人情報の方針の両方）。設定ファイルが無ければ AI がユーザーに聞く
**却下した代替案**: 都度手渡し（何を読ませたかが常にはっきりするが、手間で続かない）／まず手渡しで一周してから自動化（安全だが、指示書を2回書き直すことになる。自動で読んでも判定 JSON は目で見てからコミットするので、事故の余地は変わらない）
**確信度**: 中
**見直す条件**: AI が関係ないログまで拾って判定を水増しするようなら、読む範囲を「直近 N 件」か「日付を指定」に絞る

## 2026-09-23 AI への指示書は `prompts/judge.md` に1つ置き、判定基準は書き写さず参照させる

**論点**: Claude Code / ChatGPT に渡す判定の指示をどのファイルに、どんな形で置くか。`internal/llm/prompt.go` の文面をどう流用するか
**結論**: 指示書の本体は `prompts/judge.md` に1つだけ置く。`.claude/skills/judge-log/SKILL.md` はそれを読ませる薄い入口にする（手順だけの10行程度）。**レベルの基準（`criteria`）と根拠の種類の上限は指示書に書き写さず、`data/roadmap.json` の `levels` と `backend/internal/domain/types.go` の表を読ませる**。文面は `prompt.go` から流用し、禁止事項に `rationale` の固有名詞の禁止を1行足す
**理由**: `prompt.go` が基準をコードに書かずマスタ JSON と `domain` から差し込んでいるのは、基準を変えたときにコードを直さずに済ませるため（`../CLAUDE.md`「ハードコードは禁止」、このリポジトリの CLAUDE.md「判定基準をコードに直書きしない」）。指示書に書き写すと同じ問題が指示書に移るだけで、基準を変えたときに指示書だけ古いまま残る。Claude Code はファイルを読めるのでこれで成立し、ChatGPT で使うときは `prompts/judge.md` を貼れば同じことができる
**却下した代替案**: Claude Code のスキル1つに全部入れる（`/judge-log` と打つだけで済み最短だが、ChatGPT では使えなくなる）／指示書に基準をべた書きし、CI で「指示書とコードの表が一致するか」を検査する（検査の実装が要るうえ、ずれてから気づく形になる）／CLI に「ロードマップと現状を埋め込んだ貼り付け用プロンプト」を出力するサブコマンドを足す（ChatGPT での手貼りが正確になるが、今は要らない。**この案は捨てていない。ChatGPT で実際に不便だったら足す**）
**確信度**: 高
**見直す条件**: ChatGPT での手貼りが実際に面倒か、貼り忘れで判定がずれたら、上の却下案（貼り付け用プロンプトの生成）を足す

## 2026-09-23 検証（V1〜V8）は手元の CLI と CI の両方で走らせ、CI は理解度の一致まで見る

**論点**: AI が書いた判定 JSON の検証を、書き込み前のローカル CLI で走らせるか、CI で走らせるか
**結論**: 両方。CLI に2つのモードを持たせる。`recalc` は検証して `data/state.json` を書き出す（手元で使う）。`verify` は検証だけして、**`state.json` が計算し直した結果と一致するかも見る**。違えば終了コード1（CI で使う）
**理由**: CLI は理解度を再計算して書き出す役なのでどのみち手元で走る。CI に `verify` を置く目的は「AI が判定 JSON を書いたのに CLI を走らせ忘れた」「`state.json` を手でいじった」を止めること。一致まで見ないと、生成物だけが古いまま push できてしまう。生成物をコミットして CI で一致を確認するのは、生成物をリポジトリに置く構成での定石
**却下した代替案**: ローカルの CLI だけ（走らせ忘れたまま push できる）／CI だけ（手元で直せず、赤くなってから気づく。理解度を書き出す役がいなくなる）
**確信度**: 高
**見直す条件**: なし

## 2026-09-23 `internal/llm` の stub は v1 では使わず、フェーズ3へ棚上げする（コードとテストは残す）

**論点**: 判定の主体が Claude Code / ChatGPT に移ったあと、`LLM_PROVIDER=stub` の偽プロバイダを v1 に残すか
**結論**: 棚上げする。コードもテストも消さず、v1 の手順書（`prompts/judge.md`・README）に登場させないだけにする。`internal/llm/output.go`（AI 出力の形の検査）は 2026-09-23 の方針変更の決定どおり v1 の中核として残り、`verify` / `recalc` CLI から呼ぶ
**理由**: stub は `llm.Provider` インタフェースの実装で、それを呼ぶ相手（ワーカー）が既に棚上げ済み。呼び手のいない実装だけを v1 に残すと、`llm.New` と `internal/config` の LLM 設定まで v1 に引きずられる。画面開発に要るのは「それらしい判定 JSON」だけで、それは AI に1回出させるか手で書けば足りる。テストは残るので CI は緑のまま

**確信度**: 高
**見直す条件**: 画面開発で大量のダミー判定が要るようになったら、上の却下案（`cmd/` のダミー生成）を検討する

## 2026-09-23 skill-matrix を「公開する Web サービス」から「自分専用のツール」へ絞り込む

**論点**: v1 を、他人がログインして使う Web サービスとして完成させるか、自分ひとりが使う道具に絞るか。きっかけは「自分しか使わないならどうなるか」「学習は ChatGPT / Claude Code でしているのだから、そこから直接リポジトリを更新できるのではないか」という本人の問い直し
**結論**: 自分専用に絞る。データはリポジトリ内の JSON、判定は Claude Code / ChatGPT（サーバから Claude API を呼ばない）、検証（V1〜V8）は CI で走らせる Go、画面は静的サイトを GitHub Pages に置く。`internal/store`（PostgreSQL）・`internal/httpapi`（GitHub ログイン・セッション・CRUD）・`internal/worker`（キュー）・`internal/llm` の Claude API クライアントとプロンプト組み立て・レート制限は **消さずに棚上げし、v2「他人にも使わせる」で戻す**。`internal/domain`・`internal/roadmap`・`internal/llm/output.go`（AI 出力の形の検査）はそのまま中核として残る
**理由**: 当初の目的（`PLAN.md`「どこまで理解できているか分からない」の解消、スキルツリーでのモチベーション、面接で見せる）は**画面が無いと1つも満たされない**のに、着手から6週間で完了した実装24件のうち画面は0件だった。公開向けの部品（ログイン・DB・キュー・クォータ）が主役になり、目的から遠ざかっていた。判定を AI にやらせる理由は「自己申告が甘くなるから」であって、判定する主体はサーバ上の Claude でも手元の Claude Code でも目的は同じ。自分専用ならサーバ・DB・API キー・課金・他人の個人データがすべて不要になり、公開のハードルも同時に消える。面接用途は公開リポジトリの URL を送るだけで足りる
**却下した代替案**: 今の Web サービス方針を続ける（バックエンドは転職の見せ札として最も厚いが、画面到達まで残り約8タスクあり、公開時に費用・API キー・他人の個人データの管理が要る）／仕組みは自分用のまま検証ロジックを CLI として配布する（運用費ゼロで筋は良く、**この案は捨てていない。自分用が動いたあとの選択肢として残す**）
**確信度**: 中（「画面が無いと目的を満たせない」は確実。棚上げしたバックエンドを本当に v2 で戻すかは、自分用が動いてからでないと判断できない）
**見直す条件**: 自分用の画面まで到達し、実際に使って価値が確認できたとき。そこで「他人にも使わせたい」と思えば棚上げしたバックエンドを戻す。逆に「自分用で十分」なら CLI 配布へ進む

## 2026-09-21 `git branch -D` を deny から ask へ移し、Claude が実行する

**論点**: マージ済みのローカルブランチの削除を、2026-09-19 の判断どおりユーザーに頼み続けるか、Claude が実行できるようにするか
**結論**: `~/.claude/settings.json` の `permissions.deny` から `Bash(git branch -D *)` を外し、`permissions.ask` へ移した。Claude が「PR が MERGED」「ローカルの先端が PR の先端と一致」の 2 点を確認したうえで実行し、Auto モードでも出る手動プロンプトをユーザーが承認する。2026-09-19 の判断（実行は本人）を置き換える
**理由**: 確認の中身は 2026-09-19 から変えていない。変えたのは最後の一手を誰が打つかだけで、`ask` なら承認のプロンプトが必ず出るので「黙って消える」余地は残らない。コピペを無くすには deny から外すしかない（権限リストは deny > ask > allow の順に評価され、allow を足しても deny が残る限り実行できない。`ask` は auto モードでも必ずプロンプトになる。いずれも公式ドキュメントで確認：https://code.claude.com/docs/en/permissions.md と https://code.claude.com/docs/en/permission-modes.md ）。放置すると溜まる：この設定を見直した時点で、life-plan-simulator に 24 本、babyfood-check に 7 本、photo-prompt-builder に 2 本、app-template に 1 本のマージ済みブランチが残っていた
**却下した代替案**: 現状維持（ガードは最も固いが、ユーザーが毎回コピペする。実際どのアプリも片付いていなかった）／`allow` に入れる（プロンプトも出なくなる。確認を 1 つ見落としたときに未 push の作業が黙って消える余地が残る）／`git branch --delete --force` のように書き換えて deny をすり抜ける（拒否された操作を形を変えて通すことになる。禁止）
**確信度**: 高
**見直す条件**: 承認プロンプトが頻繁すぎて作業の妨げになったら、マージ直後にまとめて 1 回だけ消す運用に変える。逆に、確認の 2 点を満たしているのに消してはいけないブランチ（手元だけで持っている実験など）が出てきたら deny に戻す

## 2026-09-20 stub の判定は「固定の文面」ではなく「同じ入力に同じ判定」にする

**論点**: SPEC.md §4.6 は `LLM_PROVIDER=stub` を「固定レスポンスを返す」と定めていたが、実装（PR #24）は入力のロードマップから判定を組み立てる形になった。SPEC と実装のどちらに合わせるか
**結論**: 実装に合わせて SPEC を書き換える。stub は「LLM を呼ばず、同じ入力には同じ判定を返す」もので、ロードマップの先頭から未達の項目を 3 件まで選び「現在レベル + 1」を提案する。あわせて §4.5 に、V1〜V8 の前に形の検査があることを追記する
**理由**: 項目の key はロードマップごとに違う。全員に同じ文面を返すと全件が V1（実在しない項目）で弾かれ、画面開発で何も動かない。stub を置いた目的（開発中の課金ゼロ・テストの決定性）は「同じ入力に同じ出力」で満たせる。検証ルールを試すテストは、返す JSON を丸ごと指定できる別の入口でまかなう
**却下した代替案**: SPEC どおり文面を完全固定にする（サンプルのロードマップでしか動かず、自分のロードマップをインポートした時点で使えなくなる）／ログ本文のキーワードから項目を選ぶ（偽物に判定ロジックを持たせると、その正しさまでテストが要る）
**確信度**: 高
**見直す条件**: 画面開発で「特定の項目だけを狙って上げたい」場面が増え、先頭から順に埋まる挙動では確認しづらくなったら、stub が選ぶ項目を環境変数かリクエストで指定できるようにする

## 2026-08-22 スキルツリーのレイアウトは自前の階層配置（純粋関数）で描く

**論点**: 依存関係を木として描くのに、グラフ描画ライブラリを入れるか、自前で配置するか
**結論**: 自前。段 = 依存の深さ（前提なし = 0段、前提の最大段 + 1）、同じ段は定義順で横に並べる。配置計算はフロントエンドの純粋関数（Vitest で検証）、線は SVG で引く
**理由**: 分野ごとに描くなら項目は数十個までで、依存もほぼ一本道 + 少しの分岐。階層配置だけで読める。配置を純粋関数にすれば「ロジックは純粋関数で単体テスト可能に」の原則にそのまま乗り、依存ライブラリも増えない
**却下した代替案**: React Flow + dagre（パン・ズームやノードの交差回避を任せられるが、学習コストとバンドルが増える。分野ごとの規模では過剰）
**確信度**: 中
**見直す条件**: 1分野に30項目を超えるロードマップが実際に出てきて線が交差して読めない、またはロードマップ全体を1枚で描きたくなったら React Flow + dagre に切り替える

## 2026-08-22 学習パスは「縦一列」と「スキルツリー」を切り替え表示にする

**論点**: SPEC §7.2 の縦一列をスキルツリーに置き換えるか、両方残すか
**結論**: 両方残し、画面上で切り替えられるようにする。マトリクス画面はそのまま残す
**理由**: 縦一列は「次に何をやるか」を迷わず読める（順番が一意）。ツリーは「どの前提を取ると何が解放されるか」が見える。答えている問いが違うので、片方に寄せると失うものがある。データ（依存順の項目リスト + 依存関係）は共通で、描き分けだけの差なのでコストも小さい
**却下した代替案**: 学習パスをツリーに置き換える（一列の読みやすさを捨てることになる）／現状維持で印だけ付ける（「独立していないスキル」が見えない）
**確信度**: 高
**見直す条件**: 実際に使って片方しか開かなくなったら、その時点で使わない方を外す

## 2026-08-22 スキルツリーは分野ごとに描き、他分野の前提はゴーストノードで示す

**論点**: ロードマップ全体を1枚のツリーにするか、分野（domain）ごとに描くか。`dependsOn` は分野をまたげる
**結論**: 分野ごと。他分野の項目に依存している場合は、その項目を灰色のゴーストノードとして置き、クリックでその分野のツリーへ移動する
**理由**: 1ロードマップは最大500項目で、1枚では読めない。分野ごとなら最大100、現実的には6〜15項目に収まる。分野には `goal`（到達目標）があり、「この分野であと何を取ると目標に届くか」を一画面で見せる単位として自然
**却下した代替案**: 全体を1枚で描く（パン・ズーム前提になりライブラリが要る。読める範囲を超える）／分野またぎの依存を描かない（前提が見えず「なぜ解放されないか」が分からなくなる）
**確信度**: 高
**見直す条件**: ロードマップが分野またぎの依存だらけになり、ゴーストノードが分野内の項目より多くなったら全体表示を検討する
