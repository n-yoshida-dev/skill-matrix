# SPEC.md の解説

`SPEC.md` は AI（実装するとき）が参照する正本で、簡潔に書いてある。
この文書は**それを人間が読んで理解するためのもの**。何をどう決めたか、なぜそうしたかを噛み砕く。

読む順番は上から。分からない言葉が出てきたら §1 の用語集に戻る。

> **2026-09-23 に v1 の方針が変わった。** 「他人がログインして使う Web サービス」から「自分専用のツール」へ絞り込んだ
> （理由は `PLAN.md`「技術的な方針」と `logs/decisions.md` 2026-09-23）。
> この解説は Web サービス版のときに書いたもので、**§3.3〜3.5（データベース・インポート・CRUD）、§4.1（非同期）、
> §4.2（プロンプト構成）、§4.5（反映モード）、§7 と §8 の一部は v2「他人にも使わせる」の解説**になった。
> 該当する節の頭にその旨を書いてある。v1 で何が起きるかは §0 に書き直した。理解度モデル（§2）、ロードマップ JSON（§3.1）、
> 根拠の種類と8つのチェック（§4.3・§4.4）、次にやること（§5）、画面（§6）は v1 でもそのまま。

## 0. まず、このアプリで何が起きるのか

利用者（＝あなた）の1日はこうなる。

1. Go の Tour を1章やった。いつもどおり `~/workspace/study` に学習ログを書く（これは skill-matrix の外）。

   > 「Tour の Basics を終えた。`:=` と `var` の使い分けと、暗黙の型変換がないことを確認した。
   > naked return は短い関数以外では読みにくい、というのも自分の言葉で説明できた」

2. Claude Code で `/judge-log` と打つ（ChatGPT なら `prompts/judge.md` を貼る）。AI が学習ログのうちまだ判定していないものを探して読む。

3. AI がこのログを読んで、**ロードマップのどの項目に、どれくらいの理解が示されたか**を判定し、
   `data/judgments/2026-09-20-tour-basics.json` のような**ファイルを1つ足す**。

   ```
   go-01（基本構文）→ レベル2「自分で説明可能」を提案
     根拠の種類: 自分の言葉での説明
     根拠の出どころ: repo:n-yoshida-dev/study@a1b2c3d/go/logs/2026-09-20.md   ← ログ本文はリポジトリに入れず、場所だけ指す
     根拠: naked return の可読性の問題に自分の言葉で触れている
     確信度: 0.8
   ```

4. 小さなコマンド（Go の CLI）がこの提案を**そのまま鵜呑みにせず、ルールでチェックしてから** `data/state.json`（理解度）を書き直す。
   自分は `git diff` で判定の中身を見て、納得したらコミットする。CI が同じチェックをもう一度走らせる。

5. 画面（GitHub Pages の静的サイト）を開くと、マトリクス（升目の表）の `go-01` の色が濃くなっている。「次にやること」の並び順も変わる。

やることは**ログを書いて、AI に「判定して」と言うだけ**。サーバもログインも無い。
Web サービス版で予定していた「投稿ボタン → 判定中… → 結果表示」は v2 に送った。これが中核の体験。

登場するファイルは3つだけ（`SPEC.md` §3）。

| ファイル | 役割 | 誰が書くか |
|---|---|---|
| `data/roadmap.json` | ロードマップ（マスタ） | 人（AI に手伝わせてよい） |
| `data/judgments/<日付>-<名前>.json` | 判定。学習ログ1件につき1ファイル。**作ったら以後触らない** | AI（訂正は人が新しいファイルを足す） |
| `data/state.json` | 理解度。判定を順に適用した結果 | CLI だけ。**手で編集しない** |

## 1. 用語集

この文書と SPEC.md に出てくる言葉。

| 言葉 | 意味 |
|---|---|
| **ロードマップ** | 学習計画のマスタ。「分野」と「詳細項目」の入れ物 |
| **分野（domain）** | ロードマップの大きな区切り。例：Go、React / TypeScript、課金 |
| **詳細項目（item）** | 分野の中の1単位。例：`go-01 基本構文`、`go-02 メソッド・インターフェース` |
| **レベル** | 理解度。0（未着手）〜5（別文脈へ応用）の6段階 |
| **根拠（evidence）** | なぜそのレベルと判定したかの裏づけ。「ドリルに答えた」「自分の言葉で説明した」など |
| **判定（judgment）** | AI が「この項目はレベルNだ」と提案すること。**提案であって確定ではない** |
| **イベント** | 判定が確定して記録された1件のできごと。追記のみで、書き換えない |
| **マトリクス** | 分野 × 詳細項目を升目で並べた表。色の濃さがレベル |
| **fork（フォーク）** | 他人のロードマップを**その時点でまるごと自分用にコピー**すること |

## 2. 理解度をどう表すか（SPEC.md §1）

### 2.1 なぜ「点数」ではなく「段階」なのか

最初は「理解度 0〜100点」も考えた。**やめた。**

理由は2つ。

- **AI に点数を出させると安定しない。** 同じログを2回読ませて 72点 と 78点 が返ってきたとき、
  その6点の差に意味はない。でも升目の色は変わってしまう
- **段階なら「何があればそのレベルか」を文章で書ける。** そしてその文章を**そのまま AI への指示文に入れられる**。
  判定の基準が1か所（ロードマップ JSON の中）に集まる

段階はこう。これは新しく考えたものではなく、あなたが `~/workspace/study/learner-profile/skill-map.md` で
すでに運用している5段階をそのまま持ってきた。

> **2026-09-25 に「レベルの決まり方」が変わった（`SPEC.md` §1.1）。** レベルは 1 本の数直線ではなく、
> 「1〜5 それぞれに根拠の印が付いたか」の集合（`evidencedLevels`）から導く。表示するレベル（`verifiedLevel`）は
> 「1 から途切れずに印が付いている最上段」。印が `[3]` だけなら表示は 0 で、「実装の根拠はあるが基礎の確認が未了」を表す。
> 理解の梯子（1 → 2）と実装の梯子（3 → 4 → 5）は別で、**実装したからといって基礎を説明できるとは見なさない**。
> 実装に関わった直後でも基礎の説明に失点した実例があったため。

| レベル | 名前 | どうなったらこのレベルか |
|---|---|---|
| 0 | 未着手 | まだ始めていない |
| 1 | 基礎理解を確認 | ドリルや確認質問に答えられた |
| 2 | 自分で説明可能 | 自分の言葉で人に説明できる |
| 3 | ガイド付き実装 | AI や資料を見ながらなら実装できる |
| 4 | 自力実装・レビュー | 一人で実装でき、人のコードもレビューできる |
| 5 | 別文脈へ応用 | 習った場面とは違うところで使える |

### 2.2 「段階の手前の状態」という2本目の軸

レベルとは**別に**、こういうフラグを持つ。

| フラグ | 意味 |
|---|---|
| `learning` | 学習は始めたが、レベルを判定できる根拠がまだない |
| `explained_only` | 説明を受けて質問は出なかったが、理解の確認はしていない |
| `self_reported` | 「実務でやったことがある」と自己申告しただけ |

**なぜレベルとは別の軸にしたのか。** これらを「レベル0.5」のように数値に混ぜると、
「説明を受けた」と「自分で説明できた」の区別が消えてしまう。この2つは全く違う。

あなたの skill-map.md にはすでに
「『説明済み（質問が出なかった）』は理解の証明ではない」というルールが明記してある。
これを機械が守れる形にしたのがこのフラグ。

### 2.3 時間が経ったら理解度は下がるのか → 下げない

「1ヶ月前に確認したきりだから、レベルを下げる」という仕組み（減衰）は**入れない。**

理由：**自動で下がった数字は説明できない。** 「なぜ昨日より薄くなったの?」に答えられない表は信用されない。
AI の判定にブレがあるうえに減衰まで乗ると、升目の色が何を意味するのか誰にも分からなくなる。

代わりに、各項目に**「最後に根拠が付いた日」**を持つ。そこからの経過日数で3段階に分ける。

| 状態 | 経過日数 |
|---|---|
| `fresh` | 30日以内 |
| `aging` | 31〜90日 |
| `stale` | 91日以上 |

**表示は「色」と「枠線」の2つを使い分ける。**

- 升目の**色の濃さ** = レベル（0〜5）
- 升目の**枠線・斜線** = 要再確認（`stale` になった、または AI が「下がってるかも」と言った）

これなら「Go の基本構文はレベル2だが、最後の根拠が3ヶ月前だから怪しい」が一目で分かる。
しかも数字は勝手に動いていない。

## 3. ロードマップをどう持つか（SPEC.md §2, §3）

### 3.1 ロードマップは JSON ファイルで書く

分野と詳細項目の一覧を、こういう JSON で用意する（`SPEC.md` §2 に完全版）。

```jsonc
{
  "name": "SaaS エンジニア学習ロードマップ",
  "source": "https://github.com/.../curriculum.md",  // どこから持ってきたか
  "checkedAt": "2026-08-09",                          // いつ確認したか
  "levels": [
    { "level": 1, "name": "基礎理解を確認", "criteria": "ドリル・確認質問に答えられた" }
    // ... 2〜5
  ],
  "domains": [
    {
      "key": "go", "name": "Go",
      "items": [
        { "key": "go-01", "name": "基本構文", "dependsOn": [] },
        { "key": "go-02", "name": "メソッド・インターフェース", "dependsOn": ["go-01"] }
      ]
    }
  ]
}
```

ポイントが3つある。

- **`levels[].criteria` が判定基準の正本。** この文章がそのまま AI への指示に埋め込まれる。
  基準を変えたければここだけ直せばよく、プログラムを直す必要がない
- **`dependsOn` で前後関係を書ける。** 「go-02 は go-01 の後」。
  これがあると「次にやること」の順番を機械が計算できる
- **出典（`source`）と確認日（`checkedAt`）は、外部から持ってきた場合だけ必須。**
  `origin` という項目で3種類を区別する

  | `origin` | どういうロードマップか | 出典・確認日 |
  |---|---|---|
  | `manual` | 利用者が自分の頭で組んだ | **任意** |
  | `external` | 記事やカリキュラムを元にした | **必須** |
  | `builtin` | アプリに同梱するサンプル・既定ロードマップ | **必須**（元ネタがある場合） |

  共通ルールの「外部由来の定義は出典と確認日を併記」は、外部由来のものだけに掛かる。
  自分で考えたロードマップにまで出典を求めると、作るハードルが無意味に上がる。省略時は `manual` 扱い

v1 では画面からポチポチ作る機能は作らない。**`data/roadmap.json` を直接書く**だけ（AI に手伝わせてよい）。
分野が5個・項目が30個あるものを画面から入力するのは苦痛だし、あなた一人なら JSON で十分だから。
壊れた JSON は CLI（`SPEC.md` §6）が弾く。画面に貼り付けてインポートする形は v2（§3.4・§3.5）。

### 3.2 他人のロードマップを使うときは「コピー」する（fork）

これは共有機能（v2）の話だが、**データの形は v1 から決めておく必要がある**ので先に説明する。

やりたいこと：誰かが作った良いロードマップに star（いいね）を付けて、自分でも使いたい。

**素直にやるとこうなる。**

```
田中さんのロードマップ ←──── あなたの進捗が「参照」で紐づく
```

これは壊れる。田中さんがロードマップを編集したらどうなるか。

- 田中さんが `go-03` を削除した → あなたの `go-03` の判定履歴は宙に浮く
- 田中さんが `go-01` の名前を「基本構文」から「Go の文法入門」に変えた → 同じ項目とみなす? 別物?
- 田中さんが項目を10個追加した → あなたの進捗率が勝手に下がる

**そこで GitHub と同じやり方にする。**

```
田中さんのロードマップ（テンプレート）
        │
        │ fork = その時点の中身をまるごとコピー
        ↓
あなたのロードマップ（コピー）←──── あなたの進捗はこっちに紐づく
```

- **star** = ブックマーク。進捗とは無関係
- **fork** = 使うときにコピーを作る。以後、田中さんが何をしようとあなたのコピーは無傷

田中さんの更新を取り込む機能（`git pull` 相当）は、v1 では作らない。難しいわりに最初は要らないから。

### 3.3 データベースの形

> **v2 の解説。** v1 はデータベースを持たず、同じ内容をリポジトリ内の JSON で持つ（`SPEC.md` §3）。
> 下の `assessment_events`（一次データ）と `item_states`（導出値）の関係は、v1 の `data/judgments/` と `data/state.json` の関係と同じ。

テーブルの一覧は `SPEC.md` §10.1。ここでは**考え方が分かりにくい3点**だけ説明する。

#### (1) テンプレートと自分用を同じテーブルに入れている

```
roadmaps
  kind = 'template'  ← 公開されて star される側
  kind = 'personal'  ← fork したコピー。進捗はこっちに紐づく
```

分けたほうがきれいに見えるが、分けると分野・項目のテーブルも2組ずつ必要になって4テーブル増える。
中身の構造は同じなので、1つのテーブルに `kind` を持たせた。

fork は**行のコピー**になる。テンプレートの roadmaps / domains / items の行を読んで、
新しい ID で `kind='personal'` として insert し直す。それだけ。

#### (2) 理解度を「更新」せず、「できごとを積む」

ここが一番わかりにくいところ。素直に作るならこうなる。

```
-- 素直な作り（採用しない）
UPDATE item_states SET level = 2 WHERE item_id = 'go-01';
```

これをやると、**前の値が消える。** そして次の問題が起きる。

- 「なぜ `go-01` がレベル2なの?」に答えられない。根拠が残っていない
- AI の判定がおかしかったとき、巻き戻せない
- 判定ロジックを改良したとき、**過去のログを全部読み直して計算しなおすことができない**

そこで、2つのテーブルに分ける。

```
assessment_events  ← できごとの記録。追記のみ。絶対に書き換えない
  「2026-08-10、go-01 をレベル2にした。根拠は『自分の言葉での説明』。
   元になったログは #123。AI 判定。確信度0.8」
  「2026-08-15、go-01 をレベル3にした。根拠は『実装』。元ログは #131」

item_states        ← 現在の状態。上の記録から計算できる「答え合わせ済みの値」
  go-01 → レベル3、最終根拠日 2026-08-15
```

`item_states` は速く読むための**キャッシュ**であって、消えても `assessment_events` から再計算できる。

これで得られるもの：

- 「なぜこの升目が濃いのか」を根拠つきで説明できる
- 判定ルールを変えたら、全イベントを読み直して再計算できる
- 手動で直した履歴も同じ形で残る（`source = 'manual'`）

> Java で言うと、監査ログを別テーブルに持つのに近い。
> ただしこちらは**監査ログのほうが正で、現在値がそこから導かれる**という向き。

#### (3) レベル定義（`levels`）はロードマップの行に丸ごと入れる

§3.1 の JSON にある `levels`（レベル1〜5の名前と判定基準）は、`levels` 用のテーブルを作らず、
**`roadmaps` テーブルの `levels` 列に JSON のまま入れる**（列の型は `jsonb`。PostgreSQL が JSON を
そのまま保存できる型で、文字列として入れるのと違い、中身の構造を保ったまま取り出せる）。

```
roadmaps
  id     | name          | levels（jsonb）
  ...    | SaaS 学習     | [{"level":1,"name":"基礎理解を確認","criteria":"..."}, ... 5件]
```

素直に考えると `levels` テーブルを作って1レベル1行にしたくなる。そうしなかった理由は2つ。

- **レベルの意味はロードマップごとに変えたい。** Go の「ガイド付き実装」と英語学習の「ガイド付き実装」は
  同じ意味にならない。だからアプリ共通の固定値にせず、ロードマップ1つにつき1セット持つ
- **常に5件セットでしか読み書きしない。** 「レベル3だけ取り出す」という使い方が無いので、
  行に割っても JOIN（表の結合）が増えるだけで得がない

`criteria` は AI への指示文にそのまま埋め込まれる（§3.1）。つまり判定基準の正本は
`roadmaps.levels` にあり、プログラムの中には無い。理由の原文は `SPEC.md` §10.1「設計の要点」。

### 3.4 JSON を貼ったら何が起きるか（インポート。SPEC.md §10.7「インポート」）

> **v2 の解説。** v1 ではインポート API は無く、`data/roadmap.json` を直接置く。
> ただし「壊れた JSON をどう弾くか」（エラーと警告の区別、問題を全部集めて返す）は v1 の CLI（`SPEC.md` §6）でも同じ検査が走る。

`POST /api/roadmaps/import` に §3.1 の JSON をそのまま送る。アプリは**保存する前に中身を検査**し、
見つけた問題を**全部まとめて**返す。1件目で止めないのは、「直して送る、次のエラーが出る、また直す」の
往復を減らすため。

問題には2つの重さがある。

| 重さ | どうなるか | ステータス |
|---|---|---|
| **エラー**（`error`） | 1件でもあれば**保存しない**。全部直してから送り直す | 400 |
| **警告**（`warning`） | **保存する**。ただし応答で「ここが足りない」と知らせる | 201 |

線引きの考え方：**入れると後で壊れるもの**はエラー、**無くても動くが、あった方が良いもの**は警告。

具体例で見る。

- `dependsOn` を `dependOn` と打ち間違えた → **エラー**（`unknown_field`）。
  黙って受け入れると依存関係が消え、学習パスの並び順だけが静かに狂う。止める方が安全（`SPEC.md` §2）
- `go-02` が `go-03` に依存し、`go-03` も `go-02` に依存 → **エラー**（`circular_dependency`）。
  「どちらが先か」が決まらず、学習パスを計算できない
- 同じ `key` を2回書いた → **エラー**（`duplicate_key`）。判定結果をどちらの項目に付けるか決められない
- `origin` が `external` なのに `outcome` が無い項目がある → **警告**（`missing_outcome`）。
  §10 の方針どおり `outcome` は必須にせず、あとから AI 下書きで埋める
- `source` に URL ではなく書籍名を書いた → **警告**（`invalid_format`）。
  書籍で学ぶこともあるので止めない。URL なら後から確認しやすい、と伝えるだけ

同じ `missing_outcome` でも、`builtin`（アプリ同梱）ではエラーになる。
用意する側が責任を持てるから。`origin` 別の扱いは `SPEC.md` §2.1。

応答の `issues[]` には問題が1件ずつ入り、`path` が **JSON のどこか**を指す
（例：`domains[0].items[2].key` ＝ 1番目の分野の3番目の項目の key）。
JSON として読めない場合や循環参照のように、1か所を指せない問題では `path` が無い。
画面はこの `path` と `code` で「どこを直すか」を出す。応答の正確な形と `code` の一覧は `SPEC.md` §10.7。

ほかに知っておくこと：

- **インポートは毎回、新しいロードマップを作る。** 既存のものを上書きしない。
  分野や項目を直したいときは JSON を直して再インポートし、古い方は §3.5 で消す
- 作られるロードマップは常に**自分専用・非公開**（`kind='personal'`）。公開してテンプレートにするのは v2
- 大きすぎる JSON は検査に入る前に 413 で断る。1項目の文章が長すぎる場合はエラー（`too_long`）。
  どちらも AI 判定1回で読ませる量を青天井にしないための上限。値は `SPEC.md` §2 §10.7

### 3.5 自分のロードマップに何ができるか（CRUD。SPEC.md §10.7「CRUD」）

> **v2 の解説。** v1 ではロードマップは `data/roadmap.json` 1つで、編集はファイルを直接直す。

CRUD は Create（作る）・Read（読む）・Update（更新する）・Delete（消す）の頭文字。
このアプリでは次の対応になる。

| 操作 | API | できること |
|---|---|---|
| Create | `POST /api/roadmaps/import` | §3.4 のインポート |
| Read | `GET /api/roadmaps`、`GET /api/roadmaps/:id` | 一覧（最近更新した順）と、分野・項目まで含む本体 |
| Update | `PATCH /api/roadmaps/:id` | **名前と目標日だけ** |
| Delete | `DELETE /api/roadmaps/:id` | 本体ごと消す |

分野・項目の編集が無いのは、§3.1 で「画面からポチポチ作らない」と決めたのと同じ理由。
直したければ JSON を直して再インポートする。

#### 目標日の「消す」と「触らない」を分ける

`PATCH` は「変えたいものだけ送る」方式。名前だけ変えたいのに目標日まで送らせると、
画面側が常に全項目を持ち回る必要が出る。そこで**キーを書かなければ触らない**。

すると「目標日を消したい」をどう伝えるかが問題になる。書かなければ「触らない」なので、
消すには**明示的に `null` を送る**。

```jsonc
{ "name": "Go 集中コース" }               // 名前だけ変える。目標日はそのまま
{ "targetDate": "2026-12-31" }            // 目標日だけ変える
{ "targetDate": null }                    // 目標日を消す
```

Go で「キー無し」と「null」を区別する実装上の工夫は `KNOWLEDGE.md` 2026-09-14。

#### 他人のロードマップは「無い」ことにする（404）

他人のロードマップの id を指定すると、「権限がない（403）」ではなく**「存在しない（404）」**が返る。
存在しない id を指定したときと同じ応答になる。

理由：403 を返すと「その id のロードマップは**存在する**」と教えてしまう。
id を総当たりすれば「誰かのロードマップがいくつあるか」を外から数えられる。
404 に揃えれば、自分のもの以外は**あるかどうかすら分からない**。GitHub の Private リポジトリが
他人には 404 になるのと同じ考え方。

実装では「id で引いてから Go 側で持ち主を比べる」のではなく、**SQL の絞り込み条件に持ち主を入れる**。
比べる処理を書き忘れた経路が1つあるだけで漏れるから。理由の原文は `KNOWLEDGE.md` 2026-09-14。

#### 削除は取り消せない

`DELETE` すると、分野・項目だけでなく**学習ログと判定履歴も一緒に消える**
（DB の外部キーに「親が消えたら子も消す」設定を入れている。`SPEC.md` §10.1）。
§3.3 (2) の「できごとを積む」設計は書き換えを防ぐが、親ごと消えるのは別の話。
やり直しは効かないので、画面側で確認を挟む前提で考える。

## 4. AI 判定の流れ（SPEC.md §4）

### 4.1 なぜ「非同期」にするのか

> **v2 の解説。** v1 の判定は Claude Code / ChatGPT との会話の中で行うので、待つのは自分ひとりで、非同期の仕組みは要らない（`SPEC.md` §4.1）。
> 下の話は「他人が同時に投稿する」ときに必要になる。

判定は Claude API を呼ぶので、**数秒から十数秒かかる**。

同期（＝リクエストの中で待つ）にすると：

```
ブラウザ ──POST /logs──> サーバ ──15秒待つ──> Claude API
                            ↑ この間サーバの処理が1つ埋まる
```

一人で使うぶんには動く。だが公開して10人が同時に投稿すると、サーバの処理枠が全部埋まって
他の画面まで開かなくなる。

そこで**投稿と判定を切り離す**。

```
1. ブラウザ ──POST /logs──> サーバ
                              ├─ ログを保存
                              ├─ 「判定してね」という仕事をキュー（順番待ちの列）に積む
                              └─ すぐに「受け付けました。jobId=abc」を返す（202）

2. ワーカー（別プロセス）が列から仕事を取って、Claude API を呼ぶ

3. ブラウザは GET /jobs/abc を数秒おきに叩いて「終わった?」と確認する
```

**なぜ v1 から入れるのか。** 後から非同期化すると、API のレスポンス形式・フロントの画面遷移・
ワーカーのプロセス構成を全部作り直すことになる。最初から入れるほうが安い。

> 注意点：Cloud Run（デプロイ先の候補）は、**リクエストを処理していない間 CPU が絞られる**。
> ワーカーを同じサービスに同居させると仕事が進まない。別サービスにするか設定を変える必要がある。
> これは KNOWLEDGE.md にも書いてある。

### 4.2 AI に何を渡して、何を返させるか

> **v2 の解説。** v1 では Claude API を呼ばず、`prompts/judge.md` という指示書を AI に読ませる（`SPEC.md` §4.2）。
> 「レベルの基準はロードマップ JSON から読ませ、指示書に書き写さない」という考え方は下と同じ。プロンプトキャッシュの話は v1 には関係ない。
> 返させる形（`SPEC.md` §4.3）は v1 でも同じで、`evidenceRefs`（根拠の出どころ。commit 付きで 1 件以上）が増えた。

**渡すもの（プロンプト）は4つのブロックに分ける。**

| 順番 | 中身 | 全ユーザー共通? |
|---|---|---|
| 1 | 判定の役割、5段階の基準、根拠の種類の一覧、守るべきルール、出力の形式 | **共通** |
| 2 | そのロードマップの分野・項目一覧 | 個別 |
| 3 | 対象項目の現在レベルと直近の根拠 | 個別 |
| 4 | 学習ログの本文 | 個別 |

**なぜ共通のものを先頭に置くのか。** Claude API には「プロンプトキャッシュ」という仕組みがあって、
**先頭から一致している部分**は2回目以降が安くなる（約1/10）。
共通部分を先頭に固めれば、全ユーザーで使い回せる。

ただし正直に言うと、**この仕組みではキャッシュはあまり効かない。**
キャッシュの有効期限は既定5分で、1日1回投稿する使い方だと毎回冷えている。
共通部分だけは他のユーザーの投稿で温まる可能性がある、という程度。過度に期待しない。

**返させるもの（構造化出力）** は形が決まった JSON。

```jsonc
{
  "judgments": [
    {
      "itemKey": "go-01",              // どの項目か
      "proposedLevel": 2,              // 何レベルを提案するか
      "evidenceType": "self_explanation", // 根拠の種類
      "rationale": "naked return の可読性に自分の言葉で触れている", // 根拠
      "confidence": 0.8                // どれくらい自信があるか
    }
  ],
  "unmatched": ["どの項目にも当てはまらなかった記述"]
}
```

Claude API には出力の形を JSON Schema で縛る機能がある。これを使うので、
「たまに文章で返ってきてパースできない」ということは起きない。

### 4.3 根拠の種類（evidenceType）と、付く印

ここが**あなたの判断がほしいところ**の1つ。

根拠の種類を8つに分類した。そして**「その根拠でどの段に印が付くか」**を決めた（2026-09-25 に「上限」から「印」へ。`SPEC.md` §4.4）。

| 根拠の種類 | 日本語 | 付く印 |
|---|---|---|
| `drill` | ドリル・確認質問に答えた | 1 |
| `self_explanation` | 自分の言葉で説明した | 1, 2 |
| `implementation` | 実装した（AI や資料の助けを借りて） | 3 |
| `unaided_implementation` | ガイドなしで実装した / レビューした | 3, 4 |
| `cross_context` | 別の場面で使った | 3, 4, 5 |
| `learning_activity` | 読んだ・写経した | **印なし**（「学習中」の印だけ） |
| `explained_to` | **説明を受けた** | **印なし** |
| `self_report` | **自己申告** | **印なし** |

下3つが肝。「Claude に useEffect を教えてもらった」というログは、
どれだけ丁寧に書かれていても**レベルを上げない**。フラグ（`explained_only`）が立つだけ。

これはあなたの skill-map.md にある
「『説明済み』と『習熟度の昇格』は別物」というルールを、機械が守れる形にしたもの。

### 4.4 AI を信用しきらないための8つのチェック

AI が返してきた判定を、**そのまま理解度に反映しない。** 8つのルールでチェックしてから通す（v1 では CLI が、v2 ではワーカーが同じ関数を呼ぶ）。

| # | チェック | 引っかかったら |
|---|---|---|
| V1 | その `itemKey` は本当にロードマップにあるか | 捨てる（AI が項目を捏造することがある） |
| V2 | レベルは 0〜5 の整数か | 捨てる |
| V3 | 根拠の種類は8つのリストにあるか | 捨てる |
| V4 | （2026-09-25 に廃止。欠番） | ― |
| V5 | 提案した段がその根拠の梯子の範囲内か（§4.3 の表） | 範囲に切り詰める |
| V6 | **不合格の報告**（`proposedLevel: 0`。ドリルに落ちた等） | 印は付けず「要再確認」フラグを立てる |
| V7 | 確信度が 0.5 未満（AI の判定だけ） | 反映せず「レビュー待ち」にする |
| V8 | 1ログで判定できるのは20項目まで | 超えた分を捨てる |

**捨てたものは全部記録に残す。** 黙って消さない。v1 では `data/state.json` の `rejected`（棄却）・`deferred`（保留）・`events[].violations`（クランプ等）に、
v2 では DB の `llm_responses.violations` に残す（`SPEC.md` §4.5・§10.1）。
「AI が変なことを言った」という事実自体が、後でプロンプトを改善するときの材料になる。

とくに説明が要るのは V4 と V6。

- **V4（+1まで）は廃止した**：以前は「1回のログで 0 → 4 の跳躍を止める」ために入れていた。だが印のモデルでは、
  ガイドなしの実装 1 件が 3 と 4 の印を同時に付けるのは自然で、もう 1 回実証を要求するほうが不自然。
  AI の過大評価は、指示書の条件（ガイドなしと言えるのは AI からコード提示や逐次ガイドを受けていない場合だけ）と、
  コミット前に自分の目で差分を見ることで止める
- **V6（不合格の報告）**：ドリルに落ちた・説明できなかったときは、AI が `proposedLevel: 0` で報告する。
  印は付けず、レベルも下げず、「要再確認」の印（枠線）を付けるところまでにする。下げるのは人間の判断（§2.3 と同じ思想）

### 4.5 反映モード（自動 / 確認してから）

> **v2 の解説。** v1 では「確認」は `git diff` で行う。判定ファイルはコミットするまで何も確定しないので、
> 自動反映と確認モードを切り替える設定は要らない（`SPEC.md` §4.7）。確信度が低くて保留になった判定は
> `state.json` の `deferred` に残り、採用したければ `source: "manual"` の判定ファイルを自分で足す。

チェックを通った判定を、**すぐ反映するか、人が承認してから反映するか**を切り替えられる。
ユーザーごとの設定で、**既定は自動反映**。

| モード | 動き |
|---|---|
| `auto`（既定） | 判定が終わったら即座にマトリクスが更新される。結果は画面に出るので、その場で直せる |
| `confirm` | 「go-01 をレベル2にします」と提示され、採用を押すまで反映されない |

既定を自動にした理由は、このアプリの価値が「ログを書くだけで済むこと」にあるから。
毎回の確認を必須にすると、手動でチェックボックスを付けるのと手間が変わらなくなる。
一方で「AI に勝手に決められたくない」という感覚も自然なので、切り替えを用意する。

**実装上の注意**：`confirm` で保留中のものは、`assessment_events`（できごとの記録）に**書かない**。
判定内容は別テーブル（`judgment_responses`）に残しておき、承認された時点で初めてイベントを積む。
「イベントテーブルには確定したできごとだけが入る」という原則（§3.3）を崩さないため。

なお V7（確信度が0.5未満）で保留になったものは、モードに関係なく常に確認を求める。

## 5. 「次にやること」の決め方（SPEC.md §5）

スケジュールを自動で組み直す機能は作らない。**「次にやること Top 5」を出すだけ**にする。

理由：カレンダーに自動再配置する機能は作るのが大変なうえ、一度予定から外れると使われなくなる。

優先度はこの式で決める（重みは設定ファイルに出す。コードに直書きしない）。

```
優先度 = w1 × 着手できるか   （前提項目が終わってなければ 0 ＝ まだ手を出せない）
       + w2 × 伸びしろ       （最大レベル − 今のレベル）
       + w3 × 鮮度の悪さ     （古くなっていたら加点＝再確認を促す）
       + w4 × 何個の道が開くか（これを終えると着手できるようになる項目の数）
```

### 「締切の逼迫度」を式から外した

当初この式には「締切の逼迫度」も入れていた。**実装してみて、意味がないことが分かったので外した。**

理由はこうだ。締切の逼迫度は「目標日まであと何日か」から計算するので、
**ロードマップ全体で1つの値**になる。つまり全項目に同じ数を足すことになる。

```
go-01 の優先度 = ... + 0.7   ← 同じ数
go-02 の優先度 = ... + 0.7   ← 同じ数
go-03 の優先度 = ... + 0.7   ← 同じ数
```

全員に同じ数を足しても、**並び順はまったく変わらない。** 計算する意味がない。

そこで逼迫度は優先度に混ぜるのをやめ、**独立した情報として画面に出す**ことにした。

```
目標日まで残り30日 / 未着手22項目 → 1日あたり0.7項目のペースが必要です
```

こちらのほうが「間に合うのか?」という問いに直接答えている。

代わりに式へ入れたのが **「何個の道が開くか」**。
`go-01` を終えると `go-02` と `go-03` に着手できるようになる、という数だ。
**これは項目ごとに値が違うので、実際に順位を動かす。** そして「詰まりを先に解消する」という
学習の進め方としても自然になる。

表示するときは、ロードマップ JSON に書いてある2つをそのまま載せる。

- `verifyBy`（次の確認方法）＝ 次に何をすればレベルが上がるか
- `outcome`（到達状態）＝ 身につくと何ができるようになるか

```
1. go-02 メソッド・インターフェース          レベル0
   身につくと: 型に振る舞いを持たせ、インターフェースで差し替えられる
   次の確認方法: Tour Methods の後にドリル

2. go-01 基本構文                            レベル2・要再確認（最終根拠 92日前）

3. react-01 コンポーネント / props / state   レベル0
   身につくと: props で親から子へデータを渡し、state で画面を更新できる
```

**「次に何をやるか」と「やると何ができるようになるか」を毎回セットで見せる。**
前者だけだと作業リストになり、なぜやるのかが見えない。

## 6. 画面（SPEC.md §7）

v1 は3画面（マトリクス・学習パス・項目詳細）で、**どれも読むだけ**。編集はファイル操作で行う。
ログイン・ログ投稿・ログ一覧・ロードマップ管理は v2（`SPEC.md` §10.7）。
中心は**マトリクス**（今の状態）と**学習パス**（この先の道筋）の2つ。

### マトリクスと学習パスの役割分担

| 画面 | 答える問い |
|---|---|
| マトリクス | **今どこまで来たか** |
| 学習パス | **この先どういう順で進むか / どこまで身につけたら何ができるか** |

この2つが揃って初めて「先が見える」状態になる。マトリクスだけだと現在地は分かっても行き先が見えない。

### マトリクスの形が「行列」ではない理由

最初は「行 = 分野、列 = 詳細項目」の表を想定していた。**これは作れない。**

Go の詳細項目（`go-01`〜`go-06`）と React の詳細項目（`react-01`〜`react-05`）は**別のもの**。
共通の列がないので、無理に行列にすると9割が空白になる。

そこで、**分野ごとに長さが違う帯**を並べる形にする。

```
Go           ■ ■ □ □ □ □        (6項目)
React / TS   ■ ■ □ □ □          (5項目)
Java/Spring  ■ ■ ■ ■ ■ ■ ■ ■    (8項目)
```

帯の長さそのものが「その分野をどれだけ細かく追っているか」の情報にもなる。

一覧性が落ちるので、上に「分野 × レベルごとの到達項目数」のサマリーを置いて補う。

```
             未着手  L1  L2  L3  L4  L5
Go             4     2   0   0   0   0
React / TS     3     2   0   0   0   0
```

### 学習パス画面

分野を選ぶと、その分野の項目が**依存関係の順に縦一列**で並ぶ。

```
Go        目標: Java との差分を理解したうえで、Go で Web API を設計・実装・テストできる
          進捗: 6項目中2項目

  ✓ go-01  基本構文                     レベル2
           Go のコードを読んで型と値の流れを追え、Java との差分を説明できる

  ▶ go-02  メソッド・インターフェース     レベル0  ← 今ここ
           身につくと: 型に振る舞いを持たせ、インターフェースで差し替えられる
           次の確認方法: Tour Methods の後にドリル

  ・ go-03  エラーハンドリング            レベル0
  ・ go-04  並行処理                      レベル0
  ・ go-05  net/http で最小 API サーバー   レベル0
  ・ go-06  テスト                        レベル0
```

一列に潰す処理は「トポロジカルソート」という定番のアルゴリズムでできる。
`go-02` が `go-01` に依存しているなら `go-01` を先に置く、というのを全部に対してやるだけ。

**同じ分野を「スキルツリー」としても見られる（2026-08-22 に追加）。** ゲームのスキルツリーのように、
前提が上・派生が下になる階層図で、「どの前提を取ると何が解放されるか」が見える。
一列表示とは答えている問いが違う（一列 = 次に何をやるか、ツリー = 依存の形）ので、置き換えではなく
**画面上で切り替える**。ツリーは分野ごとに描き、他分野の前提は灰色のゴーストノードで示す。
グラフ描画ライブラリは入れず、「段 = 依存の深さ」で並べるだけの自前配置にした。
仕様は `SPEC.md` §7.2、判断の理由と却下した案は `logs/decisions.md`。

分類は3つだけ。

| 印 | 意味 |
|---|---|
| `✓` done | レベル1以上（一度は根拠が付いた） |
| `▶` current | 依存順に見て最初に現れる、まだ済んでいない着手可能な項目（＝到達した先端） |
| `・` upcoming | それ以外 |

### 「今ここ」と「次にやること1位」は一致しないことがある

実装してテストしたら発覚した。**この2つは別の問いに答えている。**

| | 答えている問い |
|---|---|
| 学習パスの `▶`（今ここ） | **道のりのどこまで来たか。** レベル1に達した項目の先端 |
| 次にやること の1位 | **今いちばん時間を使うべき項目。** 済んだ項目の深掘りも含む |

具体例で見るとこうなる。`go-01` がレベル1（基礎理解を確認）に達した状態：

```
学習パス:  ✓ go-01（済）    ▶ go-02（今ここ）
次にやること: 1位 go-01（レベル1 → 2 に引き上げる）
```

一見すると矛盾しているが、どちらも正しい。

- パスから見れば `go-01` は「通過した」ので、道のりの先端は `go-02` に進んでいる
- 一方で `go-01` はまだレベル1。**レベル2（自分の言葉で説明できる）に引き上げる価値がある**

このアプリは「一度やったら終わり」ではなく**レベル1〜5を深めていく**設計なので、
済んだ項目が「次にやること」に出てくるのはむしろ正常。

**ただし画面では違いが分かるように出す必要がある。**
何も工夫せずに2つ並べると「言ってることが違う」と見える。
たとえばパス上の済項目にも「深掘り候補」の印を付ける、といった対応をする。

## 7. 安全面（SPEC.md §9）

v1 は「リポジトリを Public にして画面とデータを見せる」形で公開する。守るのは次の3つ。

- **学習ログの本文はリポジトリに入れない。** ログには職場のこと、実務のこと、転職のことが混ざる。
  リポジトリに入るのは判定（どの項目が・どのレベルに・なぜ）だけで、本文の場所を `evidenceRefs` で指すにとどめる
- **判定の `rationale`（根拠）と `evidenceRefs` には技術的な事実だけを書く。** 所属先・企業名・人名・転職活動・人事評価は書かない。
  AI への指示書で縛り、コミット前に `git diff` で自分の目で見る。Public にする直前に全件を読み直す
- **API キーはどこにも置かない。** v1 はサーバから Claude を呼ばないので、そもそも持たない

「リポジトリに実データを入れない」という共通ルールに対して、判定と理解度だけは実物を入れる。これは意図した例外で、
条件は上の3つ（`SPEC.md` §9）。テストは引き続き `backend/testdata/` のダミーを使う。

> **v2 では**：Claude の API キーはバックエンドだけが持つ（フロントに置くと開発者ツールから誰でも読める）。
> 共有機能でも学習ログ本文は外に出さず、共有するのは集計後のマトリクス（色）だけ。
> 公開時はプライバシーポリシーに「学習ログをサーバに送り、Anthropic の API に渡す」と明記する（`SPEC.md` §10.9）。

## 8. コストの現実（SPEC.md §10.4）

> **v1 では API 課金が発生しない。** 判定は Claude Code / ChatGPT のサブスクリプション内で行う（`SPEC.md` §4.6）。
> 下の見積もりと stub の話は、サーバから Claude API を呼ぶ v2 のもの。

判定1回あたり、Claude Sonnet 5 で**約4.5円**（入力7,500トークン・出力500トークン想定、$1=155円）。

| 規模 | 月間の判定数 | 月額 |
|---|---|---|
| **自分ひとり（月20件）** | 20 | **約 90 円**（Haiku 4.5 なら約 30 円） |
| 100人 × 月20件 | 2,000 | 約 9,000 円 |
| 1,000人 × 月20件 | 20,000 | 約 90,000 円 |

### 自分だけで使う場合は無料にならないのか

**ならない。** Anthropic の API は使った分だけの従量課金で、ずっと使える無料枠はない。

紛らわしいのは、Claude Pro / Max のサブスクリプション（月額課金）。
**これは claude.ai と Claude Code のためのもので、自作アプリからの API 呼び出しには使えない。**
別勘定になっている。

ただし**自分ひとりなら月90円**。年間でも1,100円程度で、実質的に気にする額ではない。
安いモデル（Claude Haiku 4.5）に切り替えれば月30円まで下がる。

**それより高くつきやすいのは開発中のテスト。** 実装しながら何十回も判定を試すと、
本番より呼び出し回数が多くなる。そこで **`LLM_PROVIDER=stub`** という環境変数を用意して、
LLM を呼ばない偽物の判定役に差し替えるモードを作った。偽物はログの本文を読まず、ロードマップの先頭から
まだ上がりきっていない項目を 3 件まで選んで 1 段ずつ上げる（同じログを何度も投稿すると、マトリクスは先頭から順に埋まっていく）。
これには2つ効果がある。

- 開発中の API 課金がゼロになる
- 同じ入力なら判定結果が毎回同じになるので、**検証ルール V1〜V8 のテストが安定する**（AI の出力は毎回微妙に違うのでテストしづらい）

もう1つ、Anthropic の管理画面で**支出上限（spend limit）を設定しておく**こと。
バグで無限ループしても青天井にならないようにする。

### 1,000人規模になったら

対策は3つあり、v2 でバックエンドを戻すときは1番目だけ入れる。

1. **レート制限**（1ユーザー月100回まで。環境変数で変更可）← v2 で入れる
2. **BYOK**（各自の API キーを登録してもらう）← v2 以降。ただし人の API キーを預かる責任が発生する
3. 課金 ← ずっと先

モデル ID は環境変数（`ANTHROPIC_MODEL`）にしてあるので、
負荷が上がったら安いモデル（Claude Haiku 4.5、約1/3）に落とす逃げ道がある。

## 10. 相談したいこと：学習の「見える化」をどう作るか

「次にやること」を出したい理由として、こういう話をもらった。

> 学習者が「今どんなところまで学習出来て、どんなことをこの先勉強していくか、
> どこまで身に付ければどのような状態になれるか」ってことを見える化させる目的も大きい。
> 初学者って先が見えない。暗いトンネルの中を壁伝いに進んでいる感じ。
> それが、明かりがついて先が見えるようになるだけで精神的不安はかなり減る。

**これは今の設計では実現できていない。** いまの「次にやること Top 5」は
優先度の高い順に5件並べたリストで、答えているのは「次の一手」だけ。
「先が見える」ようにするには、あと3つ足りない。

| 見せたいこと | いまの状態 | 足りないもの |
|---|---|---|
| 今どこまで来たか | マトリクスで見える | ○ |
| この先どういう順で進むか | 見えない（Top 5 は順番の一部を切り出しただけ） | **道筋の表示** |
| どこまで身につけたら何ができるか | まったく見えない | **到達状態の記述** |

そこで提案が2つある。

### 提案A：ロードマップに「これができるようになる」を書けるようにする

いまのロードマップ JSON は項目に「名前」しか持っていない。ここに**到達状態**を足す。

```jsonc
{
  "key": "go-05",
  "name": "net/http で最小 API サーバー",
  "outcome": "Go だけで HTTP の API サーバーを立てて、ブラウザや curl から叩ける",  // ← 追加
  "dependsOn": ["go-01", "go-03"]
}
```

分野にも同じものを足す。

```jsonc
{
  "key": "go", "name": "Go",
  "goal": "Java との差分を理解したうえで、Go で Web API を設計・実装・テストできる"  // ← 追加
}
```

これがあると、画面にこう出せる。

```
次にやること
1. go-02 メソッド・インターフェース
   → 身につくと: Go の型に振る舞いを持たせ、インターフェースで差し替えられる
   → 次の確認方法: Tour Methods の後にドリル
```

**「なぜこれをやるのか」が毎回目に入る**ようになる。

### 提案B：「学習パス」画面を作る（マトリクスとは別）

マトリクスは**今の状態**を見る画面。それとは別に、**道筋**を見る画面を作る。

分野を選ぶと、その分野の項目が**依存関係の順に縦一列**に並ぶ。

```
Go        目標: Java との差分を理解したうえで、Go で Web API を設計・実装・テストできる
          進捗: 6項目中2項目（レベル1以上）

  ✓ go-01  基本構文                    レベル2
           Java の型宣言との差分を説明できる

  ▶ go-02  メソッド・インターフェース    レベル0  ← 今ここ
           身につくと: 型に振る舞いを持たせ、インターフェースで差し替えられる
           次の確認方法: Tour Methods の後にドリル

  ・ go-03  エラーハンドリング           レベル0
           身につくと: error を戻り値で扱い、wrapping で文脈を足せる

  ・ go-04  並行処理                     レベル0
  ・ go-05  net/http で最小 API サーバー  レベル0
  ・ go-06  テスト                       レベル0
```

凝ったグラフは描かない。**依存関係の順に縦に並べて、済／今ここ／この先を分けるだけ。**
それでも「あと4つで Go で API が書けるようになる」が一目で分かる。

### 決定（2026-08-10）

**提案A・B の両方を v1 に入れる。** そのうえで `outcome` の扱いを次のように決めた。

#### `outcome` は必須にしない

理由がはっきりしている。**初学者は自分のロードマップの到達状態を自分では書けない。**

「これを学ぶと何ができるようになるか」が自分で分かっているなら、
そもそも「先が見えない」という課題が存在しない。書けないから困っているのに、
書くことを必須にしたら、アプリを使い始めることすらできない。

そこで供給源を3つ用意する。

| 供給源 | どういう場合 |
|---|---|
| **外部のロードマップに書いてある** | 記事やカリキュラムを元にした（`origin='external'`） |
| **誰かが作ったものに書いてある** | 公開ロードマップを fork した（v2） |
| **AI が下書きする** | 自作した（`origin='manual'`）。空欄の項目にまとめて生成 |

`origin` 別の扱いはこう。

| `origin` | `outcome` |
|---|---|
| `manual`（自作） | **任意。** 無くてよい。AI 下書きを案内する |
| `external`（外部由来） | **推奨。** 無ければインポート時に警告し、AI 下書きを提案（インポート自体は通す） |
| `builtin`（アプリ同梱） | **必須。** 用意する側が責任を持つ |

#### AI 下書きの作り

> **v2 の作り。** v1 では `prompts/judge.md` の手順で AI に頼み、`data/roadmap.json` を直接編集させて `git diff` で見る。
> 「下書き」の印は持たない（`SPEC.md` §4.8）。

ロードマップ単位で1回、まとめて生成する（項目ごとには分けない）。判定と同じ非同期キューに乗る。

- 生成したものは**画面上で「下書き」と明示**する
- 人が編集したら「下書き」の印が外れる
- コストは小さい（1ロードマップ = 1回、判定20回分より安い）

**必ず人が手直しできる形にする。** AI の書いた到達状態が的外れなまま「先が見える」画面に出ると、
**間違った地図を渡すことになり、当初の課題をかえって悪化させる。**
