## 1. 一度に何本判定するか

- **立場**：変える。「未判定を全部、古い順」は保つが、上限の単位を「ログ 5 本」から「本人が 1 回に読む判定の件数（12 件まで）」に替える。
  12 件に達したらそこで区切って確認を取り、残りは次の回に回す（ログの途中では切らない）。
- **理由**：A のいちばん強い点は「確認する全文が増えると、読まれなくなる」で、これは事実 §4（要約で OK した）と同じ失敗の形。
  ただし 1 本ずつに戻すと、溜まった分を消化する回数が本数に比例して増え、回らない原因に戻る。本人の負担はログの本数ではなく読む判定の件数で決まるので、
  B の「12 行まで」の考え方に説得され、上限をそちらに置く。

## 2. `rationale` とログの行の突き合わせを誰がやるか

- **立場**：変える。CLI `refs` は残し、その出力（判定 1 件ごとに `rationale` とログの該当行を並べたもの）を入力にして、B の「照合役」（判定した会話を見ない別の文脈の AI）を間に入れる。
  照合役が見るのは「その行に書いてあるか」「`judge.md` のルール（記録済みの出来事の重複・技術名が出るだけの項目・不合格の扱い）に合うか」。本人には引き続き同じ行を見せる。
- **理由**：B の強い点は、試運転で実際に見つかった誤り（同じ出来事の二重判定、場面の中で正答した問いの不合格化、技術名が出るだけの項目への判定。KNOWLEDGE.md 2026-09-27）が
  **どれも行番号の誤りではなくルールの読み違い**で、`refs` では拾えず、本人も判断できないこと。禁止語の検査で「事故を待たない」と書いた以上、ここだけ事故待ちにするのは筋が通らない。
  `refs` を先に置くのは、照合役に git を組ませず、読む範囲を機械で固定するため（照合役の弱さ＝同じ系統の AI、を役目の狭さで抑える）。使用量が増える点は、12 件の上限で釣り合わせる。

## 3. コミット後の誤判定を取り消す仕組み

- **立場**：変える。足す。ただし移行の最後（本人の確認と照合役が動いてから）に置き、記録の形は「元のファイル名・判定番号・技術的な理由」を持つ `manual` の追記 1 種類に絞る。
  スキーマ（データの形）が変わるので、着手前に台帳へ 1 件記録する。
- **理由**：A の指摘のとおり、今のコードでは印を外す処理が無く、私の案の「後から `manual` で直せる」は過大評価（実装 [3] を誤って付けた場合）には成り立たない。
  事前の確認を厚くしても、公開された理解度が間違ったまま永久に残る経路が 1 本あるのは「AI の出力を信用しきらない」と矛盾する。
  それでも最後に置くのは、取り消しは誤りが起きてから効く仕組みで、起きる頻度を下げる 1・2 の段のほうが先に効くから。

## 4. 判定を始めるきっかけ

- **立場**：自分の案のまま（skill-matrix の起動時フックとダッシュボードに「未判定 n 本」。study 側は変えない）。
- **理由**：A の強い点は、ログができた瞬間に本人の手元へ次のコマンドが渡ることで、思い出す負担が最も小さい。
  それでも採らないのは、`pending` を入れればパス付きの `/judge-log <パス>` は要らなくなり（未判定は CLI が見つける）、残る価値が「思い出させる 1 行」だけになるから。
  その 1 行のために別リポジトリのスキルへ PR を出すより、skill-matrix を開いたときに件数が必ず出る側を先に試す。開く頻度が足りなければ、そのとき study の「次のアクション」に 1 行足す。
