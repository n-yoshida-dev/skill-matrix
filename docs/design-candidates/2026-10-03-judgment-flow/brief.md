# ブリーフ：学習ログを書いてから理解度が変わるまでの流れ（判定の回し方）

このブリーフは同じ内容で 3 者に渡しています。お互いの案は見えません。設計案を 1 枚だけ書いてください。

## 1. このツールは何か

skill-matrix は、ロードマップ（分野 × 詳細項目）をマスタとして、学習ログを AI に読ませて理解度を判定させ、
理解度のマトリクスと学習パスを静的サイトで見せるツール。利用者は本人 1 人（2026-09-23 に「公開する Web サービス」から絞り込んだ）。
このリポジトリは Public。学習ログの正本は別の Private リポジトリ（`~/workspace/study`）にある。

本人について：業務は Java / Spring Boot の SE で、Go と React は学習中。技術的な設計判断の材料はまだ少なく、コードの正しさは自分では判断できない（本人の申告）。
そのため、このリポジトリの正しさはテスト・型・CI と、AI の受け入れレビューで担保している。

## 2. 頼みたいこと

論点：**学習ログを書いてから画面の理解度が変わるまでの流れを、どう回すか。** どこを自動にし、どこで人が確かめるか。
この論点について、設計案を 1 枚書いてください。

## 3. 今の流れ（事実）

1. 本人は study リポジトリで Claude Code（ときどき ChatGPT）を使って学ぶ。セッションの終わりに、study 側のスキル `/study-log` が学習ログ
   （例：`go-react/logs/YYYY-MM-DD.md`）を書いてコミットする
2. skill-matrix のセッションで `/judge-log` を呼ぶ（`.claude/skills/judge-log/SKILL.md`）。中身は `prompts/judge.md` の手順で、
   `sources.local.json` から学習ログの場所を知り、未判定のログを古い順に 1 件選び、判定ファイルを `data/judgments/` に 1 つ書く
3. 同じ手順の中で `go -C backend run ./cmd/skillmatrix recalc --data ../data` を回す。判定を検査（形の検査と意味の検査 V1〜V8）し、`data/state.json` を書き直す
4. AI が判定の一覧を報告する。人が読んでから、PR にしてマージする（CI と、AI の受け入れレビューを通す）
5. CI の `verify` が、`state.json` が判定から計算し直した結果と一致するかを確かめる。画面は `data/` の JSON を読む静的サイト
   （GitHub Pages に公開するワークフローはあるが、Pages はまだ有効にしていない。今はローカルで開いて見る）

ChatGPT のようにファイルを読めない AI で判定するときは、`prompts/judge.md` の末尾「チャットに貼って使う場合」の手順で、人が材料を貼り、返ってきた JSON を人が保存する。

## 4. 使われ方の事実（2026-10-03 時点）

- `data/judgments/` は 9 ファイル。7 本は 2026-09-27 の移行（以前の台帳からの写し）で、通常の判定は 2026-09-28 の 1 回の作業で書いた 2 本だけ
- 2026-09-28 の 2 本について本人が「OK」と言ったのは、チャットで見せた一覧（ログ・項目・根拠の種類・段・確信度と、AI が短くまとめた「何を見たか」）。
  判定ファイルの `rationale` と `evidenceRefs` の全文は、本人は読んでいない
- study の学習ログは、`go-react/logs/` に 2 本、`orgflow-learning/logs/` に 5 本ある

## 5. 今の決まり（変えてもよいが、変えるなら明示する）

次の決まりは、これまで本人と合意して決めたもの。理由は `logs/decisions.md`（特に 2026-09-23 の各件と 2026-09-25 の各件）にある。
変える案なら、どの決まりをどう変えるか、なぜ変えるかを「提案」に書くこと。

- API キーを置かない。判定は Claude Code / ChatGPT のサブスクリプションの中で行い、Claude API などの従量課金を使わない
- 学習ログの本文を skill-matrix に置かない。判定は `evidenceRefs` で出どころを指すだけ
- `data/judgments/` は追記だけ（1 ログ＝1 ファイル、書いたら触らない）。`data/state.json` は手で編集せず、CLI の `recalc` が書く。CI の `verify` が一致を見る
- 判定の基準を AI への指示書に書き写さない（基準の正本は `data/roadmap.json` の `levels` と `backend/internal/domain/types.go`）
- AI の出力を信用しきらない。形の検査と V1〜V8 を通し、想定外のものは棄却・保留として残す（握りつぶさない）
- `rationale` と `evidenceRefs` には技術的な事実だけを書く（所属先・企業名・人名などを書かない）。判定はコミットされて公開される
- 画面は読むだけ（書き込み先を持たない）
- `main` へは PR 経由でだけ入れる（ブランチ保護。CI の 5 ジョブが必須）

## 7. 書くもの

- Markdown、日本語。冒頭に 1 行の要約（`一言でいうと：…`）を置き、見出しは次の 5 つで固定する
  - `## 問題の捉え方`
  - `## 提案`
  - `## 捨てた案`
  - `## リスク`
  - `## 移行の手順`
- 長さは 150 行まで。図が要るなら文字の図かコードブロックで描く
- 読み手は、3 案を比べて推薦する別の AI と、本人（初心者向けの説明が要る）。専門用語は初めて出すときに 1 行で説明する
- 「提案」には、1 回の学習から画面が変わるまでに、**本人が何回、何をするか**を具体的に書く
- 「移行の手順」は、今の形から段階的に移る順番を、1 段階＝PR 1 本の大きさで書く
- この文書は公開リポジトリに置く可能性がある。人の名前と、個人の職歴・就職活動の文脈を書かない

## 8. 守ること

- 書き出し先（依頼のときに別に伝える）以外のファイルを作らない・変えない。コミットしない。ネットワークは使わない
- 質問はできない前提で、分からないことはあなたの判断で決め、その判断を「リスク」の末尾に 1 行で書く
