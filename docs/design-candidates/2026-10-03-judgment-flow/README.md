## 3 案が最初から一致したこと

- **いちばんの問題は「人の確認が名目になっている」こと。** 2026-09-28 に本人が「OK」と言ったのは AI の要約で、公開される判定の理由の文は読んでいない
- 本人に問うのは、本人にしか答えられない 2 つだけにする：**その出来事は実際にあったか**／**公開して困る言葉はないか**。段（レベル）が妥当かは本人に問わない
- 本人が読むのは AI の要約ではなく、**公開される文の原文**
- CI に AI の判定をさせない（API キーが要る）。画面の記録ページと、CI が `recalc` を回す案は、今は採らない（Claude Code を使わない人向けで、v1.5 に残す）

## Claude（このセッション）のおすすめ

反論のあとに合流した形を採る。本人の操作は 1 回の学習につき 3 回（study で「ログを書いて」→ skill-matrix で「判定して」→ 表を読んで「OK」か「n 番は違う」）。
画面への反映（PR・CI・レビュー・マージ）は Claude が進め、GitHub Pages を有効にしたあとは自動で公開される。

段階（1 段＝PR 1 本）。**安全を固める段を先に、量を増やす段を後に置く**（B の原則。3 者とも反対していない）。

1. **確認の形を決める（文書だけ）**：本人に見せる「公開される文の原文の表」と 2 つの問い、判定の PR の完了条件の型を `prompts/judge.md` と SPEC（§3.3・§4.1・§4.7・§9。直す節の正本は TODO の完了条件）に書く。
   1 回に見せるのは 12 件まで。表にログの行も載せるか（C は載せる、B は載せない）は、表の見本を本人に見せて決める。
   マージ後、9/28 の判定 8 件をこの表で本人に見せる（Pages を有効にする前に読むか、の確認を兼ねる）
2. **禁止語の検査を `verify` に入れる**：今は AI が文字列検索して報告しているだけ。CI でも落ちるようにする。本人しか知らない言葉は、コミットしない手元の設定ファイルに書く
3. **取り消しの記録を足す**：誤って付いた印を、履歴を残したまま外せるようにする（判定のデータの形が変わるので、着手前に台帳に記録する）
4. **ログの行を引くコマンドと、突き合わせ役の AI**
5. **未判定のログを探すコマンド**：今 AI が毎回 git のコマンドを組み立てている探し方を、テスト付きのコードにする。ここでまとめて判定するようにする（本人が読む表は 1 の 12 件までのまま）
6. **skill-matrix を開いたときに「未判定 n 本」を出す**

たまっている未判定 2 本（orgflow の 09-27・09-28）は、2 のあとに今の `/judge-log` で 1 本ずつ判定し、新しい表の読みやすさを本人に確かめてもらう場にする（B の案）。

Claude の推定：段 4 の突き合わせ役は、1 回の判定でサブスクリプションの使用量を判定とほぼ同じだけ増やす（B のリスク）。使用量が気になるなら、段 4 は後回しにできる。
